TECHNICAL DEEP DIVE
=============================================================================

Why the 37-second delay?
  - Python's Global Interpreter Lock (GIL) blocks on synchronous I/O
  - Each print() to stdout/stderr causes flush (synchronous)
  - During batch preparation (0-1%), 9 verbose prints fire in sequence
  - Network I/O + terminal write = blocking the training loop startup
  - After initial burst, normal batch processing resumes (1.57s/it observed)

Why NOT a GPU issue?
  - train.py ALREADY has optimal DataLoader configuration
  - constants.py defines _optimal_num_workers() (lines 87-89)
  - DonutTrainer.train() passes all optimization flags (lines 391-394)
  - Evidence: user's terminal showed 1.57s/batch AFTER first few batches
  - GPU throughput was never the problem - I/O latency was

Print statements removed (by purpose):
  1. Dataset loading progress (4 prints in dataset_loaders.py)
     → User doesn't need to know intermediate steps
  2. Model init sample count (1 print in train.py)
     → Redundant with pipeline-level logging
  3. RAM cache operation (1 print in run_experiments.py)
     → Cache is transparent, user just needs final results
  4. OOM recovery messages (2 prints in run_experiments.py)
     → Recovery logic preserved, messages removed
